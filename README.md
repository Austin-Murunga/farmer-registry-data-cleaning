# Farmer registry: data cleaning and reconciliation

A small, reproducible work sample showing how I take a messy field-collected dataset to something a
programme team can report from. It cleans a farmer registry, reconciles it with sales data, logs every
issue and fix, and builds one indicator on the result.

> **All data here is synthetic.** It is generated by `build_sample.py` with a fixed random seed. Names are
> random combinations, and phone numbers are deliberately fictional (`07000xxxxx`). Nothing comes from a
> real organisation, farmer or customer.

**Read the write-up:** [work_sample.pdf](work_sample.pdf) (4 pages: summary for management, issue log,
cleaning rules and trade-offs, before/after results, code excerpts, indicator definitions, and how to stop
the errors at source).

## The problem

A registry of 525 rows, collected by field staff, and 1,200 sales transactions, with the problems real
field data has: double uploads, the same farmer registered twice under new IDs, conflicting versions of
a record, county names spelt 26 ways, phone numbers in several formats, dates in three formats (some
impossible), missing values, and sales that point to IDs that don't exist.

## The result

| Check | Before | After |
|---|---|---|
| Rows vs real farmers | 525 rows | 480 farmers |
| County names in use | 26 variants | 6 agreed names |
| Valid phone numbers | 78% | 95% |
| Standard county | 67% | 97% |
| Valid registration date | 83% | 98% |
| Sales linked to exactly one farmer | 91% | 98% |

Missing values and impossible dates are **flagged, not guessed**, and listed for the field team to fix.

## Main rules

- **One farmer, one ID.** Everything joins to the farmer ID, so duplicates are resolved first.
- **Conflicting versions:** the most recent update wins.
- **Re-registrations** are merged only when *both* phone and name match. Phone alone would merge
  household members who share a phone. Sales under the duplicate ID are re-pointed to the kept ID.
- **Dates** are parsed from three formats; future, pre-programme or non-existent dates are rejected.
- **SQL check:** the de-duplication is also written as a SQL window function and run in SQLite. The
  script stops if SQL and pandas disagree.

## Files

| Path | What it is |
|---|---|
| `build_sample.py` | Generates the synthetic data, cleans and reconciles it, writes the issue log and charts |
| `make_doc.py` | Builds the write-up as a Word document, and a PDF if Microsoft Word is installed |
| `data/registry_raw.csv`, `data/sales_raw.csv` | The messy inputs |
| `data/registry_clean.csv` | One row per farmer after cleaning |
| `data/issue_log.csv` | Every issue type, rows affected and action taken |
| `output/*.png` | Charts used in the write-up |

## Run it

```bash
pip install -r requirements.txt
python build_sample.py output        # data, issue log and charts
python make_doc.py output work_sample.pdf
```

Python 3.11+, pandas, NumPy, matplotlib, python-docx. SQLite comes with Python.
